# Metro-area search and the results map

How an employer finds people by metro area, and how the results get onto a map.
The rules that constrain code are summarised in `CLAUDE.md` → **Bolsa de
Talento**; this is the reasoning behind them.

## The gap this fills

`0011` removed the city and state text filters and replaced them with a ZIP and
a radius. That was right — typing "Houston" missed everyone in Katy, Pasadena and
Sugar Land, who are a short drive from the middle of it and exactly who an
employer wants. But it left a real question with no control to express it: *who
works in the Houston area?* A radius is a circle centred on a point the employer
had to pick, and picking one means already knowing which ZIP to centre on.

A **CBSA** — Core-Based Statistical Area — is OMB's answer to the same question.
It is a county with an urban core plus every surrounding county that commutes
into it: `Houston-Pasadena-The Woodlands, TX` is nine counties. It is maintained
by somebody else, derived from commuting data, and revised on a published
schedule — so it is a boundary we do not have to defend.

The two controls compose as an AND and neither replaces the other:

| Control | The question it answers |
| --- | --- |
| `Ciudad o área metropolitana` (`?metro=`) | Who is in this labour market? |
| `Código postal` + `Distancia` (`?zip=&radius=`) | Who is within this drive of here? |

## Step 5 of the spec: strict CBSA, Option A

The spec offered a choice: strict CBSA matching, or CBSA plus a ~30-mile radius
merge around the metro centre to catch people just outside the boundary. **Strict
matching**, for two reasons:

1. CBSAs are county-based and already reach far past the city line. The
   commuter-town exclusion Option B exists to fix is largely a *city name*
   problem, which is the thing being replaced.
2. This directory already ships the radius search as its own control, where the
   employer sets the distance and can see what it did. An implicit merge would
   return people they did not ask for and cannot switch off — and "why is this
   person in my Houston results?" would have no answer on the page.

The one place inclusiveness is bought is in the reference data, not in the
query — see the third-of-a-ZCTA rule below.

## The reference data

`lib/geo/us-cbsa.json`, 405 KB, `server-only`, generated by
`npm run geo:cbsa` (`scripts/build-cbsa-table.ts`). Two official files, no API
key and no account:

1. **OMB July 2023 delineations** (`list1_2023.xlsx`, published by Census) —
   county FIPS → CBSA code, CBSA title, metro/micro.
2. **2020 ZCTA → county relationship file** — ZCTA → county, with the land area
   each part contributes.

The spec's first choice was the HUD USPS crosswalk, which maps ZIP → CBSA in one
step with residential-address weights and is the better dataset. It needs a
registered HUD API token: a credential to provision, rotate and keep out of the
repo, for a file read once a year. Census asks for nothing.

### Why bundled and not a `zip_reference` table

The spec asks for a static table in Postgres. This repo already answers that
question the other way for the ZIP half of the same dataset — `us-zips.json`,
bundled and `server-only`, for the reasons at the top of `lib/geo/zip-lookup.ts`
(no API key, no per-request charge, no rate limit that bites when the product is
busy, no third party learning where users live). Splitting one reference dataset
across the bundle and the database would also make the metro a JOIN at query
time, which the spec separately says not to do.

### What the join gives up, measured

A CBSA is a set of whole counties; a ZCTA is a postal shape that ignores county
lines. On the files above:

- ~10,200 of 33,800 ZCTAs cross a county line at all.
- **6,300** cross one where the two counties disagree about which metro they are
  in, or whether they are in one.
- ~3,100 of those splits are substantial rather than a sliver.

So a rule is needed, and it is two parts (`assignZctas`):

1. The county holding the most **land area** of the ZCTA wins. Land area because
   the file carries no population; the known bias is that a large rural county
   can outweigh the small dense one people actually live in.
2. **Except** that a metro county beats a non-metro one when it holds at least a
   third of the ZCTA. Part 1 alone fails in the direction that matters — a
   commuter ZIP on a metro's rural edge, where farmland outweighs houses, comes
   out in no metro at all and its residents vanish from every metro search. That
   is the Step 5 exclusion, fixed once in the data rather than by widening every
   query. It moved **314** ZCTAs, and it can only ever move one from "no metro"
   into the neighbouring metro, never from one metro into another.

Then ZIP → ZCTA is the same five digits, with one more pass: about 7,400 ZIPs
have no ZCTA at all (PO boxes and single buildings, which have no area to
tabulate). If every ZIP in the same city and state that *did* resolve agrees on
one metro, the unmatched ZIP inherits it — a PO box sits inside the town it
serves. Where the town's ZIPs disagree, the ZIP gets no metro.

Final coverage of the 41,197 ZIPs in `us-zips.json`:

| | ZIPs |
| --- | --- |
| Resolved ZCTA → county → CBSA | 25,048 |
| Resolved by city consensus (PO boxes) | 5,521 |
| **No metro** | 10,628 (25.8%) |

That last row is not a gap. OMB deliberately leaves rural counties outside every
metro and micro area. Those people are **absent** from a metro search — never
placed in the nearest one — and are reached through the ZIP + radius filter or by
browsing unfiltered. Anyone with no US ZIP is in the same position.

### Refreshing it

`npm run geo:cbsa` rewrites the table; `npm run geo:cbsa -- --backfill`
re-derives `cbsa_code`/`cbsa_title` on every published listing. **Run both**, in
that order. The metro is denormalized onto the listing at publish time, so
without the backfill a listing keeps the delineation vintage it was published
under until its owner happens to re-publish — and nobody is going to ask them to.
Annually is plenty; the titles move more often than the boundaries.

## Resolving what the employer typed

`?metro=` accepts either a CBSA code (what the autocomplete submits internally,
and what a shared URL carries) or the words a person typed. `resolveMetroQuery`
returns one of four things, and `/empleadores` says something different for each:

| | The page's behaviour |
| --- | --- |
| `absent` | No filter, no message. |
| `exact` | Filter, and **name the metro used** — "Houston" is not what the results were filtered by, `Houston-Pasadena-The Woodlands, TX` is, and the difference is what tells the employer Katy is included. |
| `ambiguous` | **No filter**, and offer the candidates as links. Portland, Oregon and Portland, Maine are both real; picking one would answer a question the employer did not ask, and they would read the results as though it had been their choice. |
| `unknown` | No filter, and say so — the same shape as the unrecognised-ZIP message. An unexplained full directory reads as an answer. |

`/api/talent/search` reports the same three failures in an `unresolved` object,
present only when there is something to say. Both readers go through
`resolveSearchFilters` in `lib/services/talent-directory.ts`, so the page and its
own API cannot disagree about what a query string means — the same argument that
keeps the rate limit in that file rather than in the route.

### The input submits a TITLE, not a code

`MetroPicker` writes the metro's full OMB title into the box and that is what the
form submits. A hidden field carrying the code was the obvious design and is
worse twice over: the rest of `TalentFilters` is a plain GET form that works with
no JavaScript, and a control whose real value lives in a script-filled hidden
field is dead weight without hydration — the employer types "Houston", nothing is
submitted, and no message can explain it because the server never heard. And
`?metro=Houston-Pasadena-The Woodlands, TX` says what it filtered by where
`?metro=26420` does not; employers share these URLs.

### Showing the metro on a profile

`/talento/[slug]` prints the metro beside the city **only when it adds
information**. Printed unconditionally it read as the location written twice —
"📍 Miami, FL, Estados Unidos" beside "🧭 Miami-Fort Lauderdale-West Palm Beach,
FL".

`metroAddsPlace` (`lib/talent/location-label.ts`, pure) compares the city against
the metro's **lead** city, not the whole title. A CBSA title names its secondary
cities too, so testing the full string would hide the metro from the people it is
most informative for:

| City | Metro | |
| --- | --- | --- |
| Miami | Miami-Fort Lauderdale-West Palm Beach, FL | hidden — one fact twice |
| Houston | Houston-Pasadena-The Woodlands, TX | hidden |
| Katy | Houston-Pasadena-The Woodlands, TX | **shown** |
| Sugar Land | Houston-Pasadena-The Woodlands, TX | **shown** |
| Fort Lauderdale | Miami-Fort Lauderdale-West Palm Beach, FL | **shown** |
| The Woodlands | Houston-Pasadena-The Woodlands, TX | **shown** |

Containment is tested in both directions, not equality, because a lead city can
itself be compound (`Winston-Salem, NC` → lead `Winston`; `Urban Honolulu, HI`
has no hyphen but contains `Honolulu`). The state suffix comes off at the *last*
comma first, so `Chicago-Naperville-Elgin, IL-IN` does not yield `IL` as a city.

The line is prefixed "Área de", because the bare title does not say it is a metro
area.

### Availability: asked, then shown

The profile header shows availability again, and the employer filter is back —
because `0018` made the publish popup **ask** the question. Before that,
`talent-publish.ts` stamped every listing `flexible` to satisfy a not-null
column, and the header printed that placeholder as "Mi fecha de inicio es
flexible", in the first person, about something nobody had been asked.

Three things hold it together:

1. **Required everywhere, defaulted nowhere.** `availability` is a required
   parameter of `publishTalentProfile` and a required field of
   `PublishTalentBody`. A caller with no real answer cannot publish, which is
   what makes "the server never invents one" structural instead of a convention.
2. **NULL means never asked.** The column is nullable and `0018` nulled every
   placeholder row. Null renders as nothing (`labelForAvailability` returns null
   rather than a fallback label) and matches no filter, since
   `t.availability = p_availability` is false for it — `talent_search` needed no
   change at all. A fifth enum value (`no_indicada`) was rejected: it would put a
   non-answer in the same closed list as the four answers and then have to be
   excluded by hand in every filter, dropdown and label lookup.
3. **The backfill runs once.** Guarded on the column's own nullability, because
   once the popup is live `flexible` is a real answer people have chosen, and a
   re-run of a naive `update … where availability = 'flexible'` would erase it.

The cost is one more decision in the publish popup, which the directory's design
notes otherwise call a regression. The rule stands for anything derivable —
category and seniority are still read out of the finished résumé. Availability is
not in any résumé, so the real choice was "ask, or make it up". It is kept to a
decision and not a step: same popup, four radios, nothing pre-selected, and
`Continuar` waits on both the consent and the answer.

Expect the employer filter to return few people at first. Legacy listings are
null and match nothing until their owners re-publish.

### The autocomplete knows nothing about anybody

`GET /api/talent/metros?q=` returns the same 928 metros for every caller, whether
or not a single person is published in any of them. Filtering it to metros that
*have* candidates would be a nicer autocomplete and a disclosure: it would let
anyone with an account map, one keystroke at a time, which parts of the country
have people listed — a fact about our users, offered outside the rate limit that
governs searching for them.

It still sits behind the employer gate (consistency: everything under
`/api/talent/*` needs a verified employer) and carries **its own** rate limit,
`metro_lookup`, rather than a share of `directory_search`. It is driven by
keystrokes, and spending the search allowance on typeahead would lock an employer
out of the search they were typing towards.

## The map

Leaflet + OpenStreetMap tiles: free, no API key, no billing, nothing to
provision — the same reasoning that keeps the ZIP table out of a geocoding API.
Leaflet has no dependencies of its own and is used directly rather than through
`react-leaflet`; the library is imported inside the mounting effect, so it lands
in its own chunk and never runs during a server render.

### One pin per ZIP area, not per person

This is the design, not a rendering convenience. A published coordinate is the
**centroid of a postal area**, so everyone in one ZIP has the *same* coordinate
to four decimal places — a map cannot show them as separate points however it
tries. `groupByLocation` (pure, in `lib/talent/map-pins.ts`) collapses them into
one pin carrying a count, whose popup lists the people there.

That says the true thing — *this postal area holds four people* — instead of
stacking four identical markers and hiding three. It also happens to be the
privacy-preserving shape: a pin labelled "4" cannot be read as anybody's house.
The alternatives were spiderfying, a clustering library, or jitter, and jitter is
the worst of the three because it invents a position that looks precise.

Someone with no coordinates is left **off** the map rather than placed
somewhere plausible; the table below still lists them, and the map says so when
nobody at all can be placed.

### A pin opens a profile, never a résumé

The popup links to `/talento/[slug]`. Opening a résumé spends a `contact_reveal`
and writes an audit row, and a map is a surface people click around on — wiring
résumés to pins would spend an employer's allowance on curiosity and fill
somebody's disclosure log with reads that were really just panning.

### Publishing the coordinate was a decision

`latitude`/`longitude` are new on `TalentProfilePublic` and on the `returns
table` clause of both public read functions. Everything else on that type is at
city granularity or coarser; this is finer — roughly which postal area of the
city. Three things make it acceptable, and all three have to keep holding:

1. It is a **ZIP-area centroid, never an address.** We never ask for a street
   address, so there is nothing finer to leak, and the pin is shared by everyone
   in the ZIP.
2. **It was already derivable.** `distanceMiles` comes back on every radius
   search, so three searches from three ZIPs trilaterate the point exactly.
   Publishing it discloses nothing new; it stops pretending the number is hidden.
3. **It is what the ZIP was collected for.** The funnel asks for a ZIP so
   employers can find people nearby, and `PublishDialog` now names the zone —
   "tu código postal en un mapa, nunca tu dirección" — in the list of what
   employers will see, before anyone opts in. That checkbox is the entire
   consent, so a disclosure not named there is not consented to.

`postal_code` stays private. The centroid and the ZIP carry the same
information, the map needs the first, and a bare ZIP column is the shape that
ends up in a spreadsheet.

### Attribution is a licence condition

`docs/attributions.md` already said that if the directory's location data ever
became a product feature in its own right — "a map, a downloadable dataset" —
GeoNames had to be credited visibly there. It is, in the map's caption, beside
the OpenStreetMap credit that the tile layer requires. Both are rendered as
visible text, not only inside Leaflet's own control.

One thing to know about the basemap: OSM's tile servers see the employer's map
viewport. Tiles are requested by z/x/y grid cell, which at the zoom this map uses
is tens of kilometres across, and no candidate identity or coordinate is sent —
but it is the one third party this feature introduces, and the only one.
